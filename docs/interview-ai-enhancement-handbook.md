# AI 增强实现原理手册（面试防守版 · 2026-09-15）

> **这份手册是干什么的**：整个 AI 增强由 code agent 实现，你没逐行看过代码。这份手册把每项增强讲到「**能复述原理、能接住追问、数字说得出处**」的程度。
>
> **怎么用**：
> 1. 先读 §1「主链路一分钟版」——所有功能都挂在这条链上，先有地图再记细节；
> 2. 按面试重点读 §2~§10 的模块卡（每张卡 5 分钟）；
> 3. 考前 10 分钟只看 §11 数字总表 + §12 诚实边界。
>
> **记忆心法**：每张卡的「一句话」必须能脱口而出；「没有它会怎样」= 面试官问"为什么要做这个"的标准答案；锚点（类名/表名/指标名）不是让你背代码，是被逼问细节时能对上号的"存根"。

## §1 RAG 主链路一分钟版（先建地图）

用户在问答框敲下一句话，后端依次发生（10 步）：

| 步 | 发生什么 | 挂在本步的增强 |
|---|---|---|
| 1 | 鉴权 + 限流 + **扣配额**（免费额度→额度包） | token 计量计费 |
| 2 | **语义缓存查询**：问题向量化 → 余弦 ≥0.95 找历史相似问题 | 缓存三重失效（§9） |
| 3 | 未命中 → **Query Rewrite**：把口语问题改写成利于检索的查询 | — |
| 4 | **混合召回**：向量（父子分块）+ BM25 双路 → RRF 融合排名 | 向量新鲜度指纹（§3） |
| 5 | 候选充足时 **LLM Rerank** 精排 | Prompt 注册表（§8） |
| 6 | 组装 Prompt：system 提示词 + 长期记忆 + **兴趣画像** + 参考资料 + 问题 | Prompt 注册表（§8）、冷启动画像（§10） |
| 7 | **SSE 流式生成**：逐 token 回调前端；生成前先过熔断检查 | 熔断（§4）、流式取消+TTFT（§5） |
| 8 | 输出护栏：完整文本查"注入顺从短语" | — |
| 9 | **忠实度校验**：答案逐句核对引用是否真被资料支撑（异步） | — |
| 10 | 落地：会话记忆 → **摘要压缩检查** → 写语义缓存（带指纹快照）→ 语义记忆沉淀 → **即时兴趣沉淀** | 摘要压缩（§10）、指纹快照（§9）、冷启动画像（§10） |

> **一句话总纲**（被问"你的 RAG 大概什么架构"）：
> "一条检索-生成流水线：改写 → 双路召回融合 → 精排 → 带记忆和画像的 Prompt → 流式生成 → 护栏与忠实度兜底；外围是四层工程化——**缓存降本、计量计费、熔断降级、评测门禁**，我最近两个月主要做的就是把这四层补齐。"

## §2 Token 计量与按成本计费（P0-2 + 额度包 tokens 化）

**一句话**：所有模型调用统一过"计价器"，先计量后计费，让成本看得见、账算得准。

**没有它会怎样**：模型 API 按输入/输出 token 收费，但业务侧按"次数"扣配额——一次长文总结和一次短问答收一样的钱，成本与收入倒挂；且没有数据就不知道哪个功能烧钱、该不该砍。

**怎么实现的（白话）**：
1. **计量器**（`AiTokenMeter`）：每次模型调用结束，记 `feature（功能标识）+ model + 输入 token + 输出 token + 是否估算` 五元组落库。
2. **9 处接入点**：问答的完整/快速/流式三条链路、Query Rewrite、LLM Rerank、忠实度复核、发布预检 Agent、AIGC 检测、申诉复核等——全部收口在统一网关 `AiLlmGateway`，**调用方不可能漏统计**（这是把计量放在网关而不是散在各业务里的核心原因）。
3. **两种口径**：优先用模型返回的真实 usage；模型没回传时按字符估算（**1 token ≈ 2 字符**），并打 `estimated` 标记——保证成本报表不留空洞，且能区分"真数据"和"估的数据"。
4. **计费闭环**：额度包余额从"按次"升级为"按 token"——先计量出本次消耗的 token，再从钱包原子扣减；免费额度优先、超额走钱包。
5. **成本报表**：按 feature × 模型维度聚合，回答"上个月哪个功能烧了多少 token、值不值"。

**关键数字**：
- 9 处接入点；1 token ≈ 2 字符（中文文本的粗估口径）；`estimated=true` 的记录可事后审计。

**高频追问**：
- **Q：为什么估算口径是 2 字符/token？** A：中文场景下 qwen 的分词经验值大约 1~1.8 字符每 token，取 2 做保守估计（宁可少记不虚高），并且这只是 fallback——主流网关都回传真实 usage。
- **Q：计量失败会不会影响主链路？** A：不会，计量包在 try-catch 里 fail-open，业务永远优先。
- **Q：怎么防止并发重复扣费？** A：扣减用 `UPDATE ... WHERE balance >= 消耗` 的条件更新原子操作，数据库行锁保证不超扣。

## §3 向量新鲜度指纹（P0-1）

**一句话**：给每篇文章的向量配一张"内容身份证"（正文 SHA-256 指纹），文章改了向量立刻知道该重算。

**没有它会怎样**：这是 RAG 最隐蔽的失效模式——文章编辑后，**旧向量还在库里**，检索召回的还是改写前的语义，引用指向旧内容，用户完全无感知。

**怎么实现的（白话）**：
1. 向量表（`ap_article_embedding`）加一列 **`content_hash`**：入库时对文章正文算 SHA-256 存下来。
2. 每天凌晨 3:30 定时任务（`backfillEmbeddings`）**游标分页**扫全量已发布文章（每批 200 条防压库），对每篇做三态判定：
   - 没有向量/分块 → **补写**；
   - 有向量但**指纹与当前正文不一致**（被编辑过）→ **重算**；
   - 指纹一致 → **跳过**（不浪费一次 embedding 调用）。
3. 顺带清理"非已发布文章的残留向量"（下架/删除后不再可检索）。
4. 这张"身份证"同时被语义缓存复用（§9 的第三重失效就是拿它做逐篇比对）。

**关键数字**：SHA-256 指纹；每日 03:30；批 200 条；重算只对指纹不一致的文章（正常情况一天只动少数几篇，成本极低）。

**高频追问**：
- **Q：为什么不文章一更新就实时重算？** A：编辑高频时会造成 embedding 风暴；T+1 批量 + 指纹判重，每天只花"真正变了"的钱。实时场景可以挂更新事件异步触发，机制不变。
- **Q：指纹为什么选 SHA-256 而不是直接比对正文？** A：指纹定长（64 hex），DB 比对和索引友好；正文 TEXT 比对成本高且没意义——只需要知道"变没变"，不需要"变回什么"。

## §4 熔断（P1-1）

**一句话**：给 LLM 和 Embedding 装保险丝——依赖挂了就快速失败，别让每个请求都等满超时。

**没有它会怎样**：模型服务宕机时，每个请求都要等几十秒超时才报错——用户端卡死、线程池被超时请求占满，故障从"模型挂了"放大成"整个服务挂了"。

**怎么实现的（白话）**（`AiCircuitBreaker`）：
1. **计数**：每次失败往 Redis 计数器 +1（`ai:cb:llm:fail`），首次失败设 60s 过期窗口——只数"最近一分钟"的失败，历史陈账不累积。
2. **打开**：60s 窗口内连续失败 **≥5 次**，写入熔断标记（`ai:cb:llm:open`，**30 秒**过期）。
3. **快速失败**：打开期间，网关（`AiLlmGateway`）在发起调用**之前**检查标记——直接返回降级结果，不建立连接不等超时，毫秒级返回。
4. **半开恢复**：30 秒到期标记自动消失，下一个请求放行试探；试探成功 → 清零计数、熔断关闭；还失败 → 重新计数。
5. **两个细节**：① LLM 和 Embedding 是**两个独立保险丝**（`TARGET_LLM` / `TARGET_EMBEDDING`），互不牵连；② **客户端取消不计失败**（P2-3c 专门处理的）——用户关页面不是模型故障，不往计数器里掺水。

**关键数字**：阈值 5 次 / 窗口 60s / 打开 30s——全部 `@Value` 可配置。为什么 30s：模型故障的恢复粒度通常是分钟级，30s 试探一次足够灵敏又不至于每次试探都白烧一次请求。

**高频追问**：
- **Q：为什么用 Redis 而不是 JVM 内存？** A：多实例部署时熔断状态必须全集群共享——A 实例发现挂了，B 实例也要立即快速失败。
- **Q：Redis 本身挂了呢？** A：`allow()` 查询异常时 fail-open 放行——熔断器自己坏了不能把正常业务也熔了，宁可退化为"每个请求等超时"。
- **Q：失败怎么定义？** A：网关层面捕获的调用异常（超时/连接失败）。护栏命中（安全拦截）不算失败——那是正常业务行为，会误开熔断。

## §5 流式取消 + TTFT（P2-3c）

**一句话**：用户关了页面就立刻停止生成——别为看不见的答案烧 token；顺便记录"第一个字多久出来"。

**没有它会怎样**：SSE 流式是服务端闷头生成、逐段推送；用户中途关页/切走后，**后端并不知道**，模型继续把完整答案生成完——token 全烧在没人看的文本上；且取消异常如果处理不当会被当成"模型故障"误开熔断。

**怎么实现的（白话）**：
1. **感知断开**：Controller 里给 SSE 连接注册三个回调（完成/超时/出错），任一触发就把 `AtomicBoolean cancelled` 置位；发送 delta 失败同样置位。
2. **中断传播**：每次推送 delta 前先看标志位，已取消就抛 `CancellationException`——这个异常沿着回调链一路往上抛，把 Reactor 流迭代**当场打断**（模型侧提前停止出 token）。
3. **网关分类处理**（`AiLlmGateway`）：捕获到取消异常后——
   - **不计熔断失败**（取消≠故障），还做了 cause 链识别，防响应式框架把异常包一层后认不出；
   - 已生成的部分按字符估算计量入账（成本面板不留空洞），然后**丢弃**。
4. **业务侧丢弃**：`streamFastAsk` 进入取消分支——不写语义缓存、不写会话记忆、不做护栏复核（半截答案落缓存会污染后续命中）。
5. **两个指标**：`aiask_stream_ttft`（Time-To-First-Token，从请求到第一个字，反映检索+模型首响应的综合延迟）、`aiask_stream_cancelled`（取消次数，观察断连规模）。

**关键数字**：TTFT 是流式体验的金标准指标；取消场景的计量与正常路径同口径（真实 usage 优先、空 Usage 按字符估算）。

**高频追问**：
- **Q：怎么知道客户端真的断了？** A：SseEmitter 的 onError/onTimeout 回调 + 主动 send 失败（ broken pipe）三层信号；发送前先查标志位还能省一次无效 send。
- **Q：为什么不把缓存也存一半？** A：半截答案缺结尾和引用标注，用户命中了反而更差；取消的语义就是"这次作废"。
- **Q：取消后 token 已经烧了怎么办？** A：烧掉的部分照实计量（估算口径）——**省钱靠"提前打断"（只烧前几个 token），不靠"假装没花钱"**。

## §6 评测门禁 + 评测集（P1-3）

**一句话**：给检索/提示词/模型改动装"质量红绿灯"——评测跑不过，改动就不能算数；跑不出报告，视为不通过。

**没有它会怎样**：改 Prompt、调阈值、换模型全靠肉眼感受，**质量回退无人知晓**——这比"没有评测"更糟，因为有评测能力却没被流程约束住。

**怎么实现的（白话）**：
1. **评测集**：24 条黄金问答（`ai-eval/eval-questions.json`），三类样本——**事实检索**（问某技术点，标注期望命中的真实文章）、**多跳**（一题考两个知识点的关联）、**无答案拒绝**（问语料外的问题，期望"礼貌拒答"而不是编）。
2. **两组指标**：
   - 检索侧：recall@5 / recall@10（期望文章有没有被召回）；
   - 答案侧：引用精确率/召回率、未溯源率、**refusalRate**（无答案题拒答成功率，单独统计不打分）。
3. **门禁** `runGate()`：把两组指标与阈值比对（`evaluateGate` 纯函数，可单测）：
   - 平均 recall@5 ≥ **60**、引用精确率 ≥ **50**、未溯源率 ≤ **30**、拒答成功率 ≥ **50**、有效样本 ≥ **10**（百分数口径）；
   - **fail-closed**：报告缺失/带 error/召回有效题数不足，一律按 0 分判定——**评测跑不出来 ≠ 通过**；
   - 无对应样本的检查项 skipped 视为通过。
4. **端点**：`POST /api/v1/ai/eval/gate`（登录 + 最严限流：单用户 5 分钟 1 次）。

**关键数字**：24 条样本；阈值 60/50/30/50/10。为什么 recall 阈值只定 60：语料还在增长期，黄金集覆盖不全，定 90 会永远红灯失去信号意义——阈值随语料成熟逐步上调。

**高频追问**：
- **Q：为什么门禁要 fail-closed？** A：评测链路依赖 embedding 和 LLM，它们挂了评测必然跑不出来——如果这时默认"通过"，门禁就形同虚设；"跑不出来=不通过"才能守住底线。
- **Q：expectNoAnswer 是怎么评的？** A：答案有内容但引用为空 = 拒绝成功；单独统计 refusalRate，不参与精确率/召回率打分（分母分开），否则会拉脏正常题的均值。
- **Q：门禁接 CI 了吗？** A：诚实答：端点和判定逻辑已实现，**CI 定时跑还没接**（需先在联调环境跑通真实 embedding+LLM 再落时间序列报告）——见 §12 边界。

## §7 反馈回灌（P1-2）

**一句话**：用户点的每个 👎 不只是存起来——自动变成评测集候选，让"差评"变成"下次改动的输入"。

**没有它会怎样**：反馈只采集不消费 = 闭环只有前半段；差评躺在表里，改进全凭感觉。

**怎么实现的（白话）**（`AiFeedbackServiceImpl` 的"回灌"段）：
1. **差评池**：`badCases()` 按 feature/时间拉取 👎 记录。
2. **导出评测候选** `exportEvalCandidates()`：把差评整理成 `{question, goldenArticleIds:[], note:"来自用户差评..."}` 的评测集条目格式——**golden 留空是刻意的**：机器不知道"正确答案是什么"，人工补上期望召回的文章后并入 24 条评测集，下次跑门禁就覆盖这个场景。
3. **差评率告警**：`statsByFeature()` 按功能聚合 👍/👎，差评率超过 **20%** 告警——但设了**最小样本 5 条**的下限，否则 1 条差评就告警，永远在响。

**关键数字**：告警阈值 0.2、最小样本 5。

**高频追问**：
- **Q：为什么人工补 golden 而不是全自动？** A：差评只说明"用户不满意"，不代表"检索错了"（可能是语料真没有）；把判断留给人工、把搬运交给机器——半自动是当前性价比最高的形态。
- **Q：闭环的效果怎么衡量？** A：差评导出的条目在评测集里占比、以及这些场景修复后 refusal/recall 的前后对比。

## §8 Prompt 版本注册表（P2-1）

**一句话**：把 Prompt 从代码常量搬进数据库，带版本号和灰度比例——像发代码一样发 Prompt。

**没有它会怎样**：Prompt 硬编码在 Java 常量里——改一句话要重新构建部署；**无法回滚、无法灰度、无法 A/B**；出了问题日志里没有版本号，难归因。

**怎么实现的（白话）**（`AiPromptRegistry` / 表 `ap_ai_prompt`）：
1. **表结构**：`prompt_key + version` 唯一键，每行带 `content`、`rollout_percent`（0=正式版，1~99=灰度）、`enabled`。7 个种子提示词（问答系统词/改写/精排/忠实度复核/摘要/相关问题/会话压缩）。
2. **三层解析**（每个请求按序找）：
   - **灰度版**：`userId 取模 100 < rollout_percent` 命中即用（多灰度版本时 version 大的优先）——按用户稳定分流，同一用户始终看到同一版；
   - **正式版**：未命中灰度 → 用 rollout=0 的行里 **version 最大**的；
   - **代码兜底**：DB 没有行/开关关闭/DB 异常 → 回退 Java 里的 static 常量（视为 version 0）——**fail-open 保证 Prompt 系统故障不阻塞问答**。
3. **性能**：本地缓存快照 + **60 秒懒刷新**——不是每请求查库，也用了"刷新失败也推进时间戳"的技巧防止 DB 故障时每请求都重试雪崩。
4. **归因**：每次回答把实际生效的版本写进日志和响应（`promptVersions`），A/B 对比时能精确到"哪版提示词产生的这个回答"。

**关键数字**：懒刷新 60s；灰度按 `floorMod(userId, 100) < rollout_percent`。

**高频追问**：
- **Q：为什么不放 Nacos 配置？** A：Nacos 改配置是全局生效的，做不了"按用户灰度"；DB 表天然支持多版本多行并存 + 灰度字段，回滚 = 把大 version 的 enabled 关掉。
- **Q：审核链路的 Prompt 也这么热更吗？** A：**刻意没有**——合规链路的 Prompt 变更需要走审批，热更有绕过审批的风险；这条划界本身就是设计决策。
- **Q：灰度怎么观察效果？** A：靠 §8 的 promptVersions 归因 + §6 评测门禁跑 A/B 两版的指标对比。

## §9 语义缓存三重失效（P2-2）

**一句话**：缓存答案前给引用文章拍"指纹快照"，命中时逐篇验指纹——文章改了，缓存答案立刻作废。

**没有它会怎样**：原来缓存只有"过期时间 + 文章存活"两道校验；文章**被编辑**后（还活着），缓存继续返回**基于旧内容生成的答案 + 已失效的引用**——这正是 §3 指纹要解决的同款问题在缓存上的投影。

**怎么实现的（白话）**（`AiSemanticCacheServiceImpl`）：
1. **写入快照**：落缓存时，把这次回答引用的每篇文章的 `content_hash` 拍成快照（`{articleId: hash}` JSON）存进行记录。
2. **命中校验**：命中时除了 TTL 和"文章仍已发布/未删/非 AIGC"，再**逐篇比对当前指纹**——任何一篇不一致 / 向量缺失 / 快照缺 key → 判定语料已变，**驱逐**这条缓存，回退正常检索链路。
3. **兼容**：改造前存量的行没有快照（NULL）→ 退化为仅存活校验，让它们随 6h TTL 自然淘汰，不误杀。
4. **可观测**：语料变化导致的驱逐单独计数（指标 `ai_semcache_evict_stale`），和普通过期区分开。

**关键数字**：命中阈值余弦 ≥0.95；TTL 6h；单用户缓存上限 50 条。**为什么按用户隔离**：Prompt 注入了该用户的记忆和画像，跨用户复用等于泄露画像。

**高频追问**：
- **Q：三重失效会不会太严导致命中率暴跌？** A：指纹比对是几次内存级 JSON 解析 + 已在缓存行里的数据，代价远小于一次"改写+精排+生成"三连模型调用；不严的代价（返回过时答案）比严的代价（偶尔重算）大得多。
- **Q：这次改造踩过什么坑？** A：可以讲真事——SELECT 加了指纹列后，按列下标取值的地方没同步改，相似度取错列，**异常被 fail-open 吞掉伪装成"缓存未命中"**；教训是 fail-open 的 catch 会把 bug 静默化，正向命中用例才能暴露。这类"我踩过什么坑"的回答比"一切顺利"可信十倍。

## §10 画像冷启动 + 会话摘要压缩（P2-3a/b）

### 10.1 兴趣画像冷启动（三层兜底）

**一句话**：新用户没有收藏记录也能有画像——首问之后第二问开始就有个性化参考。

**没有它会怎样**：画像靠"近 30 天收藏文章的标签聚合"，新用户为空 → 个性化整段缺失，冷启动期间 RAG 完全没有"懂你"能力。

**怎么实现的（白话）**（`UserInterestServiceImpl`，三层依次兜底）：
1. **L1 收藏画像**：近 30 天收藏 → 文章标签频次 Top5（老用户，精准）；
2. **L2 即时兴趣**：L1 为空 → 读 Redis（`ai:interest:instant:{userId}`，24h TTL）——这是**首问沉淀**的：用户问完一个问题，把他这次提问**召回文章的标签**存进去（`learnFromQuery`）；所以第二问起就有画像了；
3. **L3 全站热门**：L2 也没有 → 已发布文章按点赞排序取标签 Top5（纯新用户兜底）。
4. 每层失败自动降级下一层，全链路 fail-open；日志记录每层来源（collection/instant/hot），上线后能统计冷启动各层占比。

**高频追问**：
- **Q：为什么不把用户的问题本身当兴趣？** A：问题本身已在 Prompt 里，重复注入无增量；把"问题命中的文章标签"沉淀下来，才是"问题之外"的泛化信号，还能跨请求复用。
- **Q：即时兴趣会不会很快过时？** A：24h TTL 天然滚动；新提问会合并刷新（新标签优先、容量封顶 10 个）。

### 10.2 会话摘要压缩

**一句话**：长对话不再线性膨胀——满 22 轮就把最早的 10 轮对话让 LLM 压成一条摘要，上下文体积回落。

**没有它会怎样**：会话记忆按用户存 Redis（最多 60 条消息），裁剪掉的历史直接丢失——长会话要么上下文爆 token，要么"忘了前面聊过什么"。

**怎么实现的（白话）**（`RedisConversationMemoryService`）：
1. **触发**：每轮问答落库后检查长度，达 **44 条**（约 22 轮）触发压缩；
2. **两段式**（同步极轻 + 异步干重活）：同步段只做"长度检查 + Redis SETNX 抢锁"（60s 过期，防并发重复压缩），LLM 调用在独立单线程池异步执行——**绝不拖慢用户本轮响应**；
3. **压缩**：取最早 20 条消息拼成对话片段 → LLM 压成 300 字内摘要（提示词也走 §8 注册表，key=`memory_compress`）→ **LTRIM 删掉旧头部 + LPUSH 摘要放回头部**（role=assistant，前端按普通助手消息渲染，天然兼容）；
4. **并发安全的关键**：LTRIM/LPUSH 是两条 Redis 原子命令且只动**头部**，并发的新消息 RPUSH 在**尾部**——互不干扰，不丢消息；摘要失败本次放弃，下轮再触发（fail-open）。

**关键数字**：60 条上限 / 44 条触发 / 20 条压缩成 1 条。

**高频追问**：
- **Q：为什么阈值 44 而不是 60（满了再压）？** A：留缓冲——触发是异步的，若等满 60 才触发，压缩期间新消息会顶到上限开始丢最旧内容；44 提前动手，压缩完成后总长回落到 25 左右。
- **Q：摘要丢了细节怎么办？** A：摘要只求"主题方向 + 关键事实 + 未决问题"，不求逐字还原；被压缩的是 10+ 轮前的旧对话，信息价值密度本来就低——这是工程权衡，不是技术缺陷。
