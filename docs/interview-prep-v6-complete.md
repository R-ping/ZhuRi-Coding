### AI-1 自研 RAG 社区问答 + 单篇问答/摘要

**一句话定位**：不是套现成框架，而是自己把"检索质量"和"成本"做成了可调优的管线。

**60 秒口述**：

> 用户在文章详情页或全局浮层提问，我把它做成两种形态：**社区级 RAG** 是检索多篇文章回答，**单篇问答**是答案只来自当前文章。RAG 主链路是：文章发布后把正文切段 Embedding 进 pgvector（1024 维）→ 用户提问先做**查询改写**（口语转利于检索的关键词）→ 向量召回 15 篇宽候选 → 再用一次 LLM **重排**精到 TopK → 把文章正文按序号拼进上下文生成回答，要求模型在句末标 `[n]`，前端可点击溯源到具体文章。输出走 **SSE 逐字流式**，支持最近 6 轮会话记忆解决指代。单篇问答不检索，只把这一篇 Markdown 正文（截断 1.2 万字符）当上下文，system 强制"只依据本文、没有就说明没有"。摘要走 Redis 缓存 24h，控制重复计费。

**Top 追问：**

1. **为什么先 Query Rewrite 再召回？** → 口语问句与文档书面语存在词面差异，直接向量化召回会偏。先让模型改写成保留实体和限定词的检索式，能显著提召回命中。
2. **Rewrite 和 Rerank 各是几次模型调用？失败怎么办？** → 完整路径共 3 次（rewrite + rerank + 生成）；fast 模式只 1 次生成。rewrite 失败回退原文、rerank 失败回退向量序，**所有 AI 环节失败都有降级，主链路不挂**。
3. **Rerank 是怎么做的？** → 给模型候选列表（[序号]标题），要求输出 JSON `{"selected":[...]}`，解析后按序取 TopK；候选 < 4 篇时不启用，直接按向量相似度排。
4. **引用 [n] 怎么保证不错位？** → 组装上下文时 docs 序号与 sources 列表一一对应且**不重排**；这是一个真实踩过的坑：rerank 后如果再把 sources 按相似度重排，[n] 就指错了——所以重排只发生在取文章阶段，拼上下文后顺序锁死。
5. **SSE 怎么实现的？** → 后端 SseEmitter + 专用线程池异步执行，事件协议 `delta`（文本增量）/`done`（JSON）/`error`；前端 fetch ReadableStream 按行解析 `event:`/`data:`，逐字渲染。`done` 里的全文是权威值，防流式丢字。
6. **多轮记忆怎么做的？** → 前端维护最近 ≤6 轮 history，后端用 Spring AI 的 MessageWindowChatMemory 滑窗（≤12 条消息、每条截断 200~300 字）注入，指代由模型结合历史理解，但要求引用仍只来自本轮资料。
7. **为什么用 pgvector 不用 ES 向量？** → pgvector 与业务库同生态、运维简单、量级（几千~万级文章）完全够用；ES 主要承担全文搜索，职责分离。
8. **成本怎么控？** → 摘要/单篇高频路径 Redis 缓存 24h；长文截断 1.2 万字；AI 接口登录态 + USER/IP 双维限频；fast 模式省 2/3 调用。

**别主动说/易穿帮**：别说"一开始用官方 SDK 后来迁移 Spring AI"的开发过程；被问为什么用 Spring AI → 答框架化收益（见口径防御 6）。

### AI-2 AI 发布助手（LLM Agent + Function Calling）

**一句话定位**：让模型"调用工具"而不是"凭记忆答题"——把确定性规则和检索变成可调用的能力。

**60 秒口述**：

> 作者点发布前预检，后端让模型跑一个 **Agent 流程**：注册两个 Spring AI 原生工具——①内容安全规则引擎（本地敏感词/违法类型判定），②pgvector 相似内容检索（排除作者自己、相似度 ≥0.72 才预警）。模型在对话中自主决定调用哪个工具、拿到结果后输出结构化的预检报告：是否违规、质量分、推荐标签、一句话摘要。设计点是：**规则类与检索类能力收敛成本地工具，让模型做编排和生成而不是背答案**——既利用模型的理解力，又保证判定结果确定、可审计。工具调用或模型异常时自动降级成直答模式，**发布主流程绝不阻塞**。

**Top 追问：**

1. **Function Calling 原理是什么？** → 把工具的 name/description/parameters 以 JSON Schema 随请求发给模型，模型决定"该调哪个、传什么参"，返回 tool_call；应用侧执行工具把结果作为新消息回填，模型再续写。我们用的是 Spring AI `@Tool` 注解 + MethodToolCallbackProvider 自动生成 Schema。
2. **为什么把"违规判定"做成工具而不是直接让模型判？** → 红线词是确定性的，规则引擎 100% 可复现、零幻觉；模型负责的是"哪些场景需要查、怎么综合判断"这类开放部分。工具化=确定性归本地、开放性归模型，且每次调用可记录审计。
3. **相似内容预警的阈值怎么定的？** → 0.72 是根据真实数据观察定的；要**排除作者自己**，否则作者引用自己旧文会误报。
4. **Agent 一次会调几次工具？** → 视内容而定，可能 0~2 次；做了最大步数保护防止模型空转。
5. **模型胡编工具参数怎么办？** → Schema 约束 + 执行侧校验 + 异常兜底降级直答；预检失败不阻断发布（产品上把 AI 定位成助手而非裁判）。

**别主动说**：自研 ReAct→Spring AI 的演进史（口径见防御 6）；封面多模态已从简历删除，若被旧简历问到→口径"多模态做过合规方向验证，后来产品上收窄为文本+检索为主"（若对方没提，不主动说）。

### AI-3 AI 内容审核与 UGC 治理体系

**一句话定位**：审核不是"调一次 API"，而是一条带可靠性的生产链路：红线删除、温和折叠、故障不误伤。

**60 秒口述**：

> 分两层。**发布侧**：文章/沸点提交后先进 AI 红线审核，fail-closed——审核服务异常时宁可拒绝也不放行，防止故障期间违规内容上线；审核通过按质量分回馈作者成长值。**UGC 评论侧**：文章评论和沸点评论都走"先展示后审核"——评论先落库立即可见，同时把审核任务持久化到队列表，后台延迟 5~10 秒执行；任务执行用 CAS 抢占（PENDING→PROCESSING）保证不重复处理，处理异常按指数退避重试、超 5 次降级放行（系统故障不误删正常评论），服务重启后由定时补偿任务重新拉起。处置上：红线违规物理删除并通知；温和违规（引战/阴阳/软广）再过一次 LLM 判定，命中就折叠——文章评论折叠后作者本人可见灰条（可申诉），沸点评论全局隐藏，一级评论折叠整树无痕，二级和回复也全部进了审核链。

**Top 追问：**

1. **为什么"先展示后审核"而不是先审后发？** → 体验优先，评论即时可见；代价用可靠队列弥补——任务落库+补偿，违规内容最多滞留几秒~几十秒，且删除/折叠是收敛动作。
2. **CAS 抢占具体怎么做？** → `UPDATE task SET status=PROCESSING WHERE id=? AND status=PENDING`，影响行数 0 说明已被别人抢走，直接跳过；进程内触发和定时补偿共用这一套，天然去重。
3. **为什么文章评论和沸点评论各建一张任务表？** → 两张源表 id 各自自增会撞号，而任务表的 comment_id 唯一键是全表级，共用会冲突；独立表代价小、互不污染。
4. **温和折叠的判定为什么还要再调一次模型？** → 红线模型判断的是"违不违规、删不删"，折叠判的是"不违规但破坏氛围"（引战/阴阳/软广），是两种粒度；折叠本身是可逆的温和处置。
5. **fail-closed 和降级放行矛盾吗？** → 不矛盾：红线审核**异常**时 fail-closed（怕系统故障导致违规放行），但重试超限时**降级通过**（怕把正常内容误删）——前者防"坏内容漏过"，后者防"好内容误伤"，按风险取向分开。
6. **删评论会影响回复数和热度计数吗？** → replyCount/热度是冗余计数，删除/折叠不实时回滚（与业界常见口径一致，列表按可见数据算）；这是可接受的取舍，若追求精确可以做异步对账（承认即可，别硬说没有漂移）。

**别主动说**：两张表的设计起因别讲太长；折叠"本人可见灰条"是文章侧语义、沸点是全局隐藏——两种并存原因（前端成本）可一句带过："产品上按端做了差异化"。

### J-4 发布→AI 审核→定时上线→搜索索引（最终一致）

**一句话定位**：不用 MQ 也能做到 DB 与 ES 最终一致——核心是本地消息表 + 单状态机。

**60 秒口述**：

> 审核通过的文章按作者设定的发布时间进 Redisson 延迟队列；到点执行"发布任务"：①先往本地消息表 `article_event` 插一条记录（**先落消息，保证可补偿**）→ ②条件更新把文章置为已发布（DB 置位失败会幂等自愈）→ ③同步 ES 索引，这一步直接带上发布态，**免二次更新** → ④完成即清理。消息表用**单 status 状态机**追踪（初始→DB置位失败→ES同步失败→完成）：DB 置位失败的自己重试恢复，ES 同步失败的由 **20 秒定时扫描**拉起重试，重试超限进死信告警。这样不引入 MQ，靠"本地消息表 + 定时补偿"把双写收敛到最终一致，还天然支持服务重启恢复。

**Top 追问：**

1. **为什么不用 MQ？** → 团队/项目没有现成 MQ 基础设施；这个场景"至少一次 + 可补偿"用本地表+扫描就能满足，少一个中间件少一份运维。如果量大或要削峰，会换 MQ——**能讲清取舍边界比无脑上 MQ 加分**。
2. **先落消息再置状态，为什么顺序不能反？** → 消息是"可补偿凭证"：如果先置发布态再落消息，落消息失败会导致"文章已发布但没有任何记录可追踪 ES 是否同步"，可能漏索引且无法发现；先落消息保证任何失败都有据可查。
3. **条件更新怎么做？** → `UPDATE ap_article SET status=发布 WHERE id=? AND status=待发布`，防止重复任务重复上线。
4. **ES 同步失败和 DB 失败怎么区分？** → 靠状态机不同状态（DB_SET_FAIL / ES_SYNC_FAIL），补偿器按状态走不同恢复逻辑；重试带退避，超限置死信不再打扰。
5. **和事务消息/本地消息表经典方案什么关系？** → 本质就是"本地消息表"模式（RocketMQ 事务消息也用它兜底），我把它显式建模成状态机，失败态可观测。

**别主动说**：旧版"双状态位 + 事件监听"是重构前方案——被问就答"早期版本用过事件监听双写，发现失败难追踪后收敛成现在的单状态机"，别主动提旧实现。

### J-5 行为事件总线 + @Order 责任链

**一句话定位**：一次行为触发一堆副作用，靠"顺序 + 独立降级 + 双保险幂等"保证不乱。

**60 秒口述**：

> 点赞/关注/评论等行为成功后，通过自研的事件总线按类型路由，触发一串**后置处理器责任链**：等级积分 → 文章热度 → 站内信通知 → 成就解锁 → 用户统计。责任链用 Spring `@Order` 保证执行顺序（先加经验再判断升级），每个处理器独立 try-catch，**一个挂不拖垮整条链**。防重复上做了"行为记录门控 + 唯一索引"双保险：先插行为记录、各处理器按记录判重，库里再有唯一索引兜底，消息重复/并发重放都不会重复加分重复通知。文章热度不走累加而用**单条原子 SQL 按公式重算**（点赞×3+评论×3+收藏×6+浏览），消除读改写竞态。

**Top 追问：**

1. **和 Spring 事件/消息队列什么区别？** → 自研总线 = 同进程内有序责任链，语义是"主操作成功后的事务内/后置副作用编排"，不是跨服务解耦；跨服务走 Feign，异步走 @Async/Redisson。选型理由：副作用强依赖顺序且要独立降级，框架事件订阅做不到显式排序与隔离。
2. **为什么用 @Order 而不用责任链模式手写？** → Spring 容器收集 List<Handler> + @Order 自动排序，新增处理器零改动，顺序声明式可见。
3. **行为记录门控具体怎么防重？** → 处理器先查该行为记录是否已处理过该副作用（如积分流水唯一键），记录是唯一事实源。
4. **热度为什么重算不累加？** → 累加在并发下需要行锁或 Lua，且口径变化要重放历史；单条 `UPDATE ... SET score=公式(子查询计数)` 原子执行，无锁无竞态，口径变只改一处 SQL。

### J-6 统一支付与资损兜底（课程 + 打赏）

**一句话定位**：钱的链路，每一笔都验签、幂等、可兜底。

**60 秒口述**：

> 课程购买和文章打赏共用一套支付能力，金额全部服务端计算（课程支持折扣码与抽奖 5 折券叠加，打赏限 1~10000 元并拦截打赏自己）。支付宝异步回调先做 **RSA2 验签 + app_id + 实付金额一致**多重校验，通过后用**条件更新原子抢占订单状态**（`WHERE status=待支付`）实现幂等放权/入账——回调重复通知、并发回调都只有一笔生效。Redisson 延迟队列超时自动关单，并处理一个真实竞态：**"支付成功但订单已被关"**——系统检测到该情况自动发起退款，退款以订单号为幂等键防重复退，失败进重试任务。结算按课程 7:3 月度、打赏按流水，结算表唯一索引防重复结。

**Top 追问：**

1. **为什么回调要验金额？** → 验签只证明"来自支付宝"，金额校验防"回调参数被篡改/订单金额与支付金额不一致"这类业务层问题；服务端计价兜底前端改价。
2. **条件更新幂等的 SQL 思路？** → `UPDATE order SET status=已支付 WHERE id=? AND status=待支付`，影响行数=1 才执行入账/发奖，天然只生效一次，比"先查后改"安全。
3. **关单和支付成功的竞态怎么产生？** → 用户在超时关单前后完成了支付：关单在前、回调在后，订单已关闭，钱进来了——所以要在回调里判断"已关单但支付成功"主动退款，避免用户付了钱拿不到权益。
4. **退款幂等键为什么用订单号？** → 退款接口重复调用不能退两次；以订单号为唯一约束，第二次直接幂等返回。
5. **结算为什么防重？** → 月度结算跑批可能重复执行，唯一索引（结算周期+商户）保证只结一次。

### J-7 双 Token 无感续期 + 网关信任链 + 分层限流

**一句话定位**：登录态安全 + 内部信任链 + 防刷，三件事在网关层做干净。

**60 秒口述**：

> 认证收敛到网关：JWT Access Token(1h) + UUID Refresh Token(7d)。刷新走 Redis Lua **"取即删"原子轮换**——并发刷新只有一个能拿到新 token，杜绝竞态与重放。Access 过期网关返 444，前端收到后自动用 refresh 刷新并重放原请求，用户无感；登出在服务端吊销。**内部信任链**：网关验签后把 userId 等身份注入请求头，并用 HMAC 对关键头签名，下游只信网关透传的身份——防外部伪造 userId 越权、也防服务间被直接调用绕过网关；ThreadLocal 存身份、请求结束必须清理，防 Tomcat 线程复用串号。防刷分三层：网关按 IP 固定窗口（普通 600/分、敏感 60/分，Redis 异常 fail-open 不拖垮链路）、自定义 @RateLimit 注解（Redis+Lua 滑动窗口，支持全局/IP/用户多维叠加，NOSCRIPT 自动重载脚本）、拦截器令牌桶兜底。

**Top 追问：**

1. **JWT 为什么不放 Redis 做服务端校验？** → JWT 无状态、网关验签即可，适合分布式；refresh 走 Redis 是为了能吊销和轮换。黑名单/登出靠 refresh 吊销实现。
2. **刷新并发竞态具体是什么？** → 两个请求同时拿旧 refresh 刷新，若不轮换会各自发新 token，旧 token 还能用；"取即删"保证旧 refresh 只能被一个请求消费，拿到新 token 后旧 refresh 立即失效。
3. **444 状态码是标准吗？** → 不是，是网关自定义"需要刷新重放"的信号，前端拦截器统一处理，避免把业务错误和登录过期混在一起。
4. **HMAC 签名防什么？** → 防两件事：外部请求绕过网关直接打下游服务伪造 userId；网关本身被绕过后的身份注入。密钥服务端私有，签名只在内网链路校验。
5. **滑动窗口 Lua 怎么避免并发计数错乱？** → 计数和过期判断在 Lua 脚本里原子完成；脚本丢失（Redis 重启清脚本）时报 NOSCRIPT，代码检测到后重新加载再执行（自愈）。
6. **fail-open 会不会被刷？** → 限流组件故障时放行但降级日志告警，选择"可用性优先"；真正高危接口（支付）另有签名/风控兜底，不单靠限流。

## 3. 基础高频速答（技术一面查漏，每题一句话+支撑）

### JVM / 内存

- **内存分区**：堆（新生代 Eden+双 Survivor、老年代）、元空间、虚拟机栈、本地方法栈、程序计数器；对象主要堆上，线程栈存引用。
- **如何判断垃圾**：可达性分析，GC Roots（栈引用/静态/常量/JNI）。
- **GC 收集器/策略**：新生代复制、老年代标记-整理/清除；CMS/G1 原理一句话（G1 按 Region、可预测停顿，JDK9+ 默认）。
- **OOM 排查**：heap dump 分析（MAT/jmap）→ 大对象/泄漏嫌疑（静态集合、连接未关、ThreadLocal 未清理）。
- **类加载**：双亲委派——父加载器优先，防止核心类被篡改；打破场景（SPI/热部署）。

### 并发

- **线程池 7 参**：core、max、keepAlive、unit、workQueue、threadFactory、拒绝策略；流程：core 满→进队列→队列满→扩到 max→拒绝。
- **拒绝策略**：Abort/CallerRuns/Discard/DiscardOldest；业务上 CallerRuns 保吞吐不丢。
- **synchronized vs ReentrantLock**：JVM 层（偏向/轻量锁升级）vs API 层（可中断/超时/公平/多条件），性能差距已很小。
- **volatile**：可见性 + 禁止重排，不保证原子；单写多读场景用。
- **CAS**：比较并交换，ABA 用版本号解决；Java 里 AtomicXXX/LongAdder。
- **AQS**：ReentrantLock/CountDownLatch/Semaphore 的共同骨架——CLH 变体队列 + state。
- **ThreadLocal**：线程私有副本，**用后 remove**（线程池复用会串数据——项目里 ThreadLocal 清理就是这个原因）。

### MySQL

- **索引结构**：B+ 树——非叶子只存键、叶子链表有序，范围查询友好、树矮 IO 少；为什么不用哈希（范围）、红黑树（太高）。
- **聚簇 vs 二级索引**：聚簇叶子=整行，二级叶子=主键，回表概念；**覆盖索引**避免回表。
- **最左前缀**：联合索引(a,b,c)，查询必须从 a 开始；范围列后面的列失效。
- **事务隔离**：读未提交/读已提交/可重复读/串行化；MySQL 默认可重复读（配合间隙锁防幻读）。
- **MVCC**：undo log 版本链 + ReadView；RC 每次读新快照，RR 事务内快照一致。
- **行锁/间隙锁/临键锁**：InnoDB 默认 RR 下对范围加临键锁防幻读；**更新必须走索引，否则锁全表**。
- **explain 看什么**：type（system/const/ref/range/index/ALL）、key、rows、Extra（filesort/using temporary 要优化）。
- **慢查询优化套路**：加索引→覆盖索引→改写 SQL→必要时冗余/汇总表。

### Redis

- **穿透**（查不存在→打 DB）：布隆过滤器/缓存空值；**击穿**（热点 key 过期）：互斥重建/逻辑过期；**雪崩**（大量同时过期/实例挂）：过期加随机、集群高可用。
- **分布式锁**：SET NX EX + 唯一 value（防误删别人锁）+ Lua 原子释放；Redisson 看门狗续期；**锁的粒度要小**（项目用 Redisson 做延迟队列/锁）。
- **持久化**：RDB（快照，恢复快丢数据多）vs AOF（追加，可 everysec）；混合。
- **为什么快**：内存 + 单线程（IO 多路复用，避免锁竞争）。
- **数据类型场景**：String 计数/缓存、Hash 对象、List 消息/时间线、Set 去重/关注、ZSet 排行榜/延迟（score=时间戳）。

### Spring

- **IOC/AOP** 一句话；**Bean 生命周期**：实例化→属性填充→Aware→BeanPostProcessor（before→init→after）→使用→销毁。
- **事务失效场景**（高频）：同类自调用（代理不生效）、方法非 public、异常被吞（没配 rollbackFor=Exception 且抛的是检查异常）、类没被 Spring 管理、数据库不支持事务。
- **事务传播**：REQUIRED/REQUIRES_NEW/NESTED 至少讲清这三个。
- **@Transactional 原理**：AOP 代理 + 事务管理器；自调用失效解释同上。

### 微服务/项目通用

- **服务发现**：Nacos 注册 + 心跳续约；**Feign 调用链**：负载均衡→请求→降级（fallback）。
- **网关职责**：路由、鉴权、限流、跨域、日志；为什么把认证放网关（单点收敛，下游无状态可信）。
- **幂等三件套**：唯一键/状态机条件更新/去重表；**最终一致常见方案**：本地消息表、事务消息、定时对账。
- **分布式事务**：能不用就不用；需要时 2PC/TCC/本地消息表 各一句话区别。
- **接口设计规范**：入参校验、统一返回、null 不返（项目全局 Jackson 空值序列化）、日志、限流、幂等。

## 4. AI 基础速答（被 AI 岗追问时兜底）

- **RAG vs 微调**：RAG=检索增强+不改权重，答案可溯源、知识可更新、成本低；微调=改模型行为/风格/格式。落地优先 RAG。
- **Embedding 相似度**：向量余弦相似度；检索 = query 向量与库向量 topK。
- **幻觉怎么缓解**：限定仅依据资料、无资料明说、引用溯源、输出护栏；治本靠检索质量与 prompt 约束。
- **Prompt 注入**：用户输入里藏指令试图劫持/越权——输入净化+边界包裹、system 加固、输出顺从短语检测（项目里三层防御 + 流式兜底）。
- **Function Calling / 工具调用**：模型不执行代码，只输出"该调哪个工具+参数"，由应用侧执行并把结果回填（讲清这个就能过）。
- **流式（SSE）为什么逐字**：token 增量返回提升首字延迟体验。
- **上下文窗口与成本**：token 计费、长文截断、缓存、限频——你项目里全有实例。
- **评估**：检索侧看召回命中（命中率），生成侧人工抽查+引用正确性；重排质量看排序是否更相关。

## 2. 新增弹药卡

### AI-3（合并条）AI 内容治理与诚信体系

**一句话定位**：治理不是"调一次审核 API"，而是"**自动处置 + 可纠正**"的闭环——处置要可靠，误伤要能翻案。

**60 秒口述**：

> 分三块。**① UGC 治理**：评论和沸点评论"先展示后审核"，审核任务落库成可靠队列——CAS 抢占防重复、指数退避重试、超限降级放行不误伤、服务重启由定时任务补偿拉起；红线违规物理删除并通知，温和违规（引战/阴阳/软广）再由 LLM 二次判定折叠，文章评论折叠后作者本人可见灰条、沸点全局隐藏，一级评论折叠整树无痕。**② AIGC 水文检测**：三层判定——L1 用四维信号快检（重复度、模板化、爆发式、锚点信息），45 分触发复核、70 分触发标注；L2 算新文与作者历史文章向量均值的偏离度做作者画像（历史不足 3 篇不算）；L3 只在最终分 ≥70 时才调 LLM 复核，且模型判正常就**纠偏清标**，防误伤。检测结果一处产出、多点消费：打赏闸门、课程订单拦截、向量库与检索过滤、对外"疑似 AI 生成"标识。**③ 申诉闭环**：被处置内容可申诉，AI 按类型复核给"解除/维持"建议但**不终决**，人工终审一键解除（评论恢复可见 / 文章清标注），申诉幂等、并且加了防自审护栏——申诉人不能审自己的申诉。

**Top 追问：**

1. **为什么检测要分三层？直接让 LLM 判不行吗？** → 成本和延迟：LLM 判一次要几秒且按量计费，而绝大多数内容一眼可判。所以用便宜的统计信号做前置漏斗（L1），只有高分嫌疑才升级到 L2/L3；这样 90% 内容零 LLM 成本，同时保留 LLM 的判断力。
2. **阈值 45 / 70 怎么来的？** → 基于样本观察定的两档语义：45 是"值得复核"，70 是"值得标注/限制"——**诚实说这是小样本调参的初始值**，上线后要靠反馈与申诉数据回归修正（我把申诉结果也当作标注信号）。
3. **L2 作者画像具体算什么？** → 取作者历史已发布且非水文的文章（3~10 篇）做向量均值，再算新文与均值的余弦偏离度：延续自己风格 → 偏离小 → 不判可疑；风格突变且模板化 → 偏离大。这是"个人基线"而不是"全站基线"，避免误伤文风独特的作者。
4. **纠偏清标是什么？** → L3 模型如果判 normal，就把已标注的状态回滚（清掉标记与分数），即**模型有推翻前置分数的权力**——宁可漏判也不误伤，因为误伤的代价是作者被关闭打赏/课程售卖。
5. **检测结果被多处消费，怎么保证一致？** → 统一落在文章/沸点/课程章节的标记字段（`is_aigc`/`aigc_score`）+ 检测记录表留痕；消费侧统一"读标记"而不各自重算，向量入库与检索也过滤标记为水文的文章——**一处判定、多端只读**，避免各写各的。
6. **申诉为什么 AI 不终决？** → 定位问题：AI 的强项是压缩决策面（给建议、给证据摘要），弱项是承担责任。所以 AI 只出"解除/维持 + 置信度 + 理由"，终审权留人；这既是产品定位（平台不当裁判），也是风险控制（避免 AI 全权撤销处置）。
7. **申诉的幂等和防刷怎么做？** → 同一内容存在处理中的申诉就拒绝重复提交；状态机（待审/已解除/已驳回）单向流转；终审接口校验"申诉人 ≠ 终审人"防自审；提交侧还有用户维度限频。
8. **折叠可申诉、那删除呢？** → 红线违规是物理删除（不可申诉），温和折叠才是可逆处置——**处置强度与可逆性匹配**：越轻的处置越应该可翻案，越重的处置越需要确定性证据。

**别主动说**：不要编"检测准确率 XX%"（没有大规模标注数据）；不要把"申诉 AI 预审"说成"AI 自动放行"。

### AI-4 语义搜索与相似推荐（向量能力二次复用）

**一句话定位**：同一套向量基建，同时服务问答检索、搜索兜底与内容推荐——**且只在关键词不够用时才花语义成本**。

**60 秒口述**：

> 平台原本搜索是 ES 的 BM25 关键词，用户换个说法就搜不到。我加了一条语义通道：查询向量化后去 pgvector 召回，但**不是每次搜索都跑**——只在第一页且关键词命中数明显不足时才触发（口语化、同义词、换词场景），召回结果按 id 去重后补足这一页；关键词命中充足时完全不动原排序，保证精度与成本。跨服务调用走 Feign，语义服务不可用时降级为纯关键词、不阻断搜索。另一处复用是详情页右侧的"相似文章"：直接拿本文已有的向量在库里找最近邻，排除自身、过滤已发布非水文，没有向量就回退同标签逻辑——**推荐和 RAG 问答共用同一个向量库和过滤口径**，没有为推荐再建一套。

**Top 追问：**

1. **为什么不直接做全量混合检索（hybrid）？** → 取舍：全量混排要解决"两路分数怎么归一、怎么和分页/高亮兼容"，改动面大、收益不确定；我选的是**"关键词为主 + 语义兜底"**——只在关键词失效的场景补召回，精度不受影响、成本可控、前端零改动。如果后续数据证明语义召回质量稳定，再演进成全量混排。
2. **怎么判断"关键词命中不足"？** → 第一页且 ES 命中数低于页大小（说明召回薄），才触发语义兜底；第二页起不触发（避免重复计费与翻页抖动）。
3. **两路结果怎么融合？** → 当前是"补足"而不是"重排"：ES 结果原序在前，语义候选去重后追加到列表尾部，并且带 `semantic` 标记，前端将来可以单独展示成"更多相关内容"卡片。**不改变原有排序 = 不引入回归风险**。
4. **为什么不把向量库放在搜索服务里？** → 向量库与文章内容同库（pgvector 和文章表在一起），而 ES 在搜索服务——把向量检索放在内容侧、搜索服务通过 Feign 调，职责是"谁有数据谁提供能力"；同时内容侧已有内容过滤口径（已发布、非水文），复用最自然。
5. **跨服务调用的失败怎么办？** → Feign 配了 fallback：语义服务超时或不可用返回降级响应，搜索侧捕获后只返回关键词结果，**搜索主链路不受影响**（这也是我坚持"语义只是兜底"的一个原因）。
6. **相似推荐会不会老是推同质内容？** → 目前是纯语义相似（embedding 最近邻），确实偏同质；可以加多样性约束（同作者限 1 篇、标签去重）——**这是我知道的下一步**，别把它说成已经做了。
7. **推荐的成本是多少？** → 相似推荐是**零模型调用**：文章向量在发布时已经算好入库，推荐只是一次向量近邻查询，纯 DB 成本。

**别主动说**：别说"实现了工业级 hybrid ranking"；如实说是"兜底式语义召回 + 向量复用推荐"。

### AI-5 AI 商业化工程（可衡量 → 可变现 → 可复用）

**一句话定位**：把 AI 从"免费功能"变成"**能衡量、能收费、能复用**"的工程闭环——先能衡量，再能变现。

**60 秒口述**：

> 我按三段做。**可衡量**：问答加 👍/👎 反馈闭环（同一用户同一问题只记一次，重复反馈走更新）；建了一个 12 条真实问答对的离线评测集，用 Recall@5/@10 量化检索质量，作为改 rewrite/rerank/阈值时的回归基线；再加功能级调用指标和用户兴趣画像注入（用户近 30 天收藏文章的标签 Top5，注入时明确告诉模型"不相关就忽略、回答依据仍只来自资料"）。**可变现**：每日免费配额（Redis 按自然日计数、异常 fail-open 不阻断服务）+ AI 额度包钱包——购买走支付宝，回调按订单号前缀分发到充值服务，金额以服务端订单为准防篡改，入账后消费**优先扣钱包余额、用尽才用免费额度**，扣减用 `UPDATE ... WHERE balance > 0` 原子扣防止超扣。**可复用**：发布预检产出的摘要和标签已经回填到文章元数据，我再把它复用成公开的 AI 速读页做 SEO 入口，一份生成成本被列表摘要、详情摘要卡、速读页多次使用。

**Top 追问：**

1. **为什么免费额度是 20 次/天？** → 是"够用但不鼓励滥用"的初始值：正常用户一天问不了 20 次；成本上相当于给每个活跃用户封了每日上限。**诚实说这是拍的初始值，会按真实用量分布调**。
2. **为什么消费优先扣钱包，而不是先用免费额度？** → 两个考虑：一是已购额度对用户是"沉没的承诺"，先兑现；二是防止"免费额度永远够用、付费包一直躺着"导致退款与体验问题。**这是个产品取舍，我能讲清两种顺序的利弊**。
3. **原子扣减为什么不用 Redis？** → 额度是钱（付费购买），**DB 是唯一真源**：`UPDATE wallet SET balance = balance - 1 WHERE user_id = ? AND balance > 0`，影响行数为 0 就是余额不足——单条 SQL 天然原子，不需要分布式锁，也不存在 Redis 与 DB 不一致的问题。免费配额那种"丢了也无所谓"的计数才放 Redis。
4. **回调为什么用订单号前缀分发？** → 支付回调入口是共用的（课程订单也在那里）。给 AI 额度包用 `ai` 前缀的订单号，回调时按前缀分流到充值服务——**改动最小、不动课程订单逻辑**，也顺便证明了这套支付回调是"可扩展的通道"而不是写死的。
5. **金额校验为什么必须做？** → 回调参数可被伪造/篡改，必须以服务端订单的金额为唯一依据做一致性校验，不匹配直接拒绝——这是支付链路的基本功（课程订单同理）。
6. **评测集怎么用？改 Prompt 前后各跑一次？** → 对：任何影响检索的改动（rewrite 提示词、rerank、阈值、切分策略）前后各跑一次，看 Recall@5/@10 是涨还是跌，**避免"凭感觉优化"**；它只覆盖检索质量，生成侧目前靠人工抽查（诚实边界）。
7. **画像注入会不会让答案跑偏？** → 风险真实存在，所以做了三重约束：只注入标签词（不注入原文）、提示词里写明"仅在相关时辅助理解、不相关请忽略"、并强调"回答依据仍只来自参考资料"；而且注入只加在社区问答，单篇问答不加（避免无关上下文污染"只答本文"）。
8. **模型路由现在有几个模型？** → 诚实说：目前是**单模型 + 路由层就绪**——路由组件按"功能 → 模型"映射决策，注册表自动收集所有 ChatModel Bean，配置未命中就兜底默认模型；这样将来加低成本兜底模型或做灰度时，**业务代码零改动**。别说"已经双模型跑量"。

**别主动说**：不要说"已经产生收入"；不要说"完整的评测体系"（只是检索 recall 基线）；额度包支付链路代码完整但**沙箱回调未真实跑通**（见第 5 节边界清单）。

### J-5（口述补充）异步任务可靠性与补偿体系（横向）

**一句话定位**：项目里所有"后台异步任务"用的是同一套可靠性模式，不是各写各的。

**60 秒口述**：

> 我项目里有四处异步任务：评论审核任务、文章发布的消息表、退款重试任务、还有申诉的 AI 预审。它们的可靠性模式是统一的：**① 任务先落库**（有据可查、重启不丢）→ **② CAS 抢占状态**（`WHERE status = 待处理` 的条件更新，谁抢到谁处理，天然防重复）→ **③ 失败按指数退避重试**（60s × 2ⁿ，封顶次数）→ **④ 定时扫描补偿**（漏掉的、卡在处理中的由定时任务重新拉起）→ **⑤ 超限后的处置分两种**：影响用户体验的降级放行（审核超限放行，不误伤正常内容），涉及资金的进死信告警（退款重试超限人工介入）。这套模式让异步链路"崩溃可恢复、失败可重试、不重复执行、不误伤"。

**Top 追问**：为什么不用 MQ（无基础设施 + 规模不需要，见 J-1）；CAS 抢占和分布式锁的区别（条件更新更轻、天然幂等）；补偿扫描频率怎么定（20s，与延迟容忍度匹配）；死信怎么处理（告警 + 人工/后续补偿）。

## 2. 新增弹药卡

### 块 A｜父子分块检索（small-to-big）

**一句话定位**：**检索用小块、回答用大块**——把"一篇文章一条向量"拆成"一篇多段子块"，召回粒度从"篇"降到"段"。

**60 秒口述**：

> 原来的问题有两个：一篇文章只存一条向量，而且生成 embedding 时只取正文前 2000 字符——长技术文的后半部分对检索几乎不可见；而且句子级的提问去匹配"整篇向量"，粒度太粗。我的做法是 **small-to-big**：入库时按段落切成子块（目标 500 字、相邻块重叠 80 字、单篇封顶 30 块控成本），切分是四级降级——先按空行分段，长了按行聚合，再长按句末标点聚合，遇到无标点的压缩代码就定长硬切；相邻块保留尾部重叠、而且重叠尽量落在句子边界上，避免半句被割裂。召回时按"每篇文章最相似的子块"排序（SQL 里 `GROUP BY article_id` 取 `MAX(余弦)`），命中的是段落，但 **回答上下文仍然取整篇父块**——这就是 small-to-big。发布时同步写块，老语料由凌晨的回填任务补齐（我把它从"只补文章向量"改成"文章向量缺失才补、分块缺失才补"）。

**Top 追问：**

1. **块大小 500 字怎么定的？** → 三个约束的交点：① embedding 模型对长文本会稀释语义，块太大等于回到"整篇一条向量"；② 块太小会碎（一段完整论述被切开），召回噪声上升；③ 成本——块数越多，发布时 embedding 调用越多（我封顶 30 块）。**诚实说这是起始值**，要靠评测集回归调，不是拍脑袋的最优解。
2. **重叠为什么是 80 字？** → 重叠是为了让跨块的句子和指代不丢上下文，取块长的 15% 左右；实现上还做了个细节：**从句子边界开始截重叠**，如果截出来的内容太短（不足重叠的一半）就退回按字符截——我第一版就是这里出的 bug，当句子边界恰好落在块尾时截出来是空串，**重叠静默失效**，单测跑出来才发现的。
3. **"父块"具体是什么？回答会不会被无关段落干扰？** → 父块就是整篇文章的正文（沿用原有的每篇 1200 字符上下文预算）。这里是个取舍：子块保证"能召回"，父块保证"上下文完整"；如果将来要做更精细的，可以把父块收缩成"命中子块 + 前后各一块"的窗口——**这是我知道的下一步**。
4. **分块为什么不做语义分块（用 embedding 相似度判断切点）？** → 语义分块效果更好但成本更高（入库时要算相邻句相似度，且每篇文章都要算一次）。我选的是**结构分块（段落/句边界）+ 定量兜底**，因为它零额外模型调用、结果可预期、可复现；等评测数据证明结构分块是瓶颈再上语义分块。
5. **向量库索引建了吗？** → 刻意没建 ANN 索引：当前量级（文章数 × ≤30 块）精确扫描完全够用，而且**小数据量下 IVFFlat 反而可能漏召回**（需要训练、probes 默认 1）。我在迁移脚本里留了注释化的 HNSW 建索引语句，语料涨上来直接启用。
6. **召回用 `MAX` 聚合会不会丢信息？** → 会——同一篇文章的多个命中块只保留最相似的那个分数。这对我有利：**每篇文章只占一个候选位**，避免同一篇文章用多个块霸榜挤掉其他文章；代价是丢掉了"多块都命中"这个信号（本来可以当加强分）。这是明确的取舍。
7. **切分有没有考虑 Markdown？** → 有：入库前先过一遍内容归一化（把旧版 JSON 块内容转成 Markdown 正文），否则会把 JSON 结构当正文切。

**别主动说**：别说"做了语义分块"或"做了父块窗口收缩"；别说"分块后 recall 提升了 X%"（**数据还没跑**）。

### 块 B｜BM25 + 向量 RRF 混合召回

**一句话定位**：两路召回**只融合排名、不融合分数**——因为 BM25 的 `_score` 和向量余弦量纲根本不可比。

**60 秒口述**：

> 纯向量召回有个明显短板：**术语和代码类查询**——比如"@Transactional 失效场景""Redis 分布式锁误删"，这种词向量抓不住，而 BM25 恰恰是强项；反过来口语化提问（"锁怎么会删错别人的"）BM25 又经常全空。所以我做了混合召回：向量路走我的父子分块子块召回，BM25 路走 search 服务的 ES（`title + content` 多字段查询），两路结果用 **RRF 倒数排名融合**——`score = Σ 1/(k + rank)`，k 取 60，只用到名次。为什么不用加权分数？两路分数一个是余弦、一个是 BM25 分，**量纲不可比**，加权必须先归一化还得调参，而 RRF 只用排名、超参只有 k，更稳。融合后候选顺序就是融合顺序，我特意把原来"按向量相似度重排"的逻辑删掉了，否则融合白做。降级是分层的：BM25 服务挂了 Feign fallback 返回空列表 → 退化成纯向量；向量空了 → 只用 BM25；另外 BM25 独有命中的文章没有余弦值，我用它已存的文章向量**在本地算一次余弦**补上，来源卡片不出现编造的相似度。

**Top 追问：**

1. **为什么不用加权融合（比如 0.7×向量 + 0.3×BM25）？** → ① 量纲不可比，必须先归一化，而归一化方式又引入新参数；② 权重需要标注数据调，我没有；③ RRF 只依赖排名，对两路分数量纲不敏感、无需训练、超参只有 k，**工程上更稳**。代价是丢掉了"分数差距"信息（一个 0.99 和一个 0.51 的向量命中在 RRF 里被当成相邻名次）——这是我接受的取舍。
2. **k=60 是什么？为什么是 60？** → k 是平滑常数，来自 RRF 原论文的默认值：k 越大，靠前名次的优势越平缓，避免"某一路的第一名"单方面霸榜。60 是业界常用默认值，我没有为它单独调参（诚实说）。
3. **如果某篇文章只被 BM25 召回，它的相似度哪来的？** → 我拿了它已经存在库里的文章级向量，在应用侧本地算一次余弦（纯 CPU、**零模型调用、零额外 DB 往返之外的依赖**）。这样来源卡片展示的"相似度"仍然是真实的余弦值，不是拿融合分冒充。
4. **两路各取多少候选？** → 都取 15（原来的宽召回数），融合后再交给 LLM 重排。我没有放大召回量——因为在有 LLM 精排的前提下，**融合的价值是"把 BM25 独有的命中送进重排视野"**，而不是把候选堆大。
5. **BM25 端点为什么不做语义兜底？不怕召回不足吗？** → 必须不做：search 服务本身在"关键词命中不足"时会调 content 的语义端点，如果我在 BM25 端点里再触发语义兜底，就成了 **content → search → content 的回环**。端点的语义就是"只给我关键词排名"。
6. **BM25 端点为什么按相关度排序？** → 用户搜索接口是按 `publishTime` 倒序（要"最新"），但 RRF 吃的是**排名**，所以我给内部端点传查询时**不指定 sort，保留 ES 默认的 `_score` 降序**。这点如果搞错，融合的就是时间序，整个 RRF 就废了。
7. **跨服务调用失败怎么办？** → Feign fallback 返回**空列表**（不是抛异常）——调用方看到空就自动退化成纯向量召回，问答主链路不受影响。这和同文件里"同步文章"必须抛异常的语义刻意不同：**同步失败必须暴露，召回失败只需降级**。
8. **评测怎么跟上？** → 离线评测和线上**共用同一个召回入口**（一个 `HybridRecallService`），否则我改了融合策略、评测还在测纯向量，recall 数字就是自欺欺人。

**别主动说**：别说"hybrid 检索全面上线"；别说"融合后效果提升明显"（**对比数据还没跑**）。

### 块 C｜相似问题语义缓存（成本工程）

**一句话定位**：**用向量相似度缓存"问过的问题"，命中直接返回——省掉一次问答里最贵的三次模型调用**。

**60 秒口述**：

> RAG 一次问答要花三次模型调用：查询改写、LLM 重排、答案生成。我加了语义缓存：新问题先向量化，在**该用户自己的**历史问答里找问题向量余弦 ≥0.95 的记录，命中就直接返回缓存答案，跳过后面全部模型调用；代价只是多一次 embedding——**账很划算**。为什么按用户隔离？因为我的答案 prompt 里注入了用户长期记忆和阅读兴趣画像，**跨用户复用等于泄露画像**。失效做了双保险：TTL 6 小时兜底，外加命中时校验引用文章仍然"已发布、未删除、非 AIGC"，不满足就删掉这条缓存、回退正常链路。另外我刻意**不缓存指代类问题**（"它怎么用""上面提到的那篇"）——语义相似不代表意图相同，这类问题缓存的危险大于收益；答案太短（多为"知识库暂未找到"）也不缓存。流式问答命中时，我把缓存答案按 40 字切片走同一条 delta 通道回放，**前端完全无感**，协议不用改。

**Top 追问：**

1. **0.95 这个阈值怎么定？为什么不是 0.9？** → 这是"召回精确率 vs 命中率"的取舍：阈值越低命中越多但越容易答非所问（缓存回的是另一个问题的答案），阈值越高越安全但命中率下降。我取 0.95 是**偏保守**的初始值——宁可少命中，也不能返错答案；这个数应该用真实问答日志回归（把"命中后被用户点👎"当负信号）。
2. **为什么按用户隔离，而不是全局共享缓存？** → 答案 prompt 注入了【长期记忆】和【用户兴趣参考】两块个性化上下文，同一个问题不同用户的答案本就可能不同——**全局缓存会把别人的画像泄露给当前用户**。牺牲命中率换正确性和隐私，这个取舍我不犹豫。
3. **缓存怎么失效？文章删了怎么办？** → 双保险：① TTL 6h 到期自然失效；② 每次命中都校验答案引用的文章是否仍然"已发布 + 未删 + 非 AIGC"，只要有一篇失效就**删掉这条缓存并回退正常链路**（重新检索、重新生成）。文章下架、被判 AI 水文都会触发失效。
4. **付费额度包的用户被缓存命中，会退钱吗？** → 不会，**命中仍消耗配额**——因为配额扣减在 Controller 层、缓存判定在 Service 层（我特意没有把扣减下沉，避免扩大改动面）。这是我明确知道的取舍：对用户略不友好，但实现上没有一致性风险。**如果要做"命中不扣费"，正确的是把扣减下沉到回答成功之后**——这是可以立即执行的下一步。
5. **缓存会不会把"错答案"固化下来？** → 有一定风险，我用三件事收敛：① 阈值保守；② TTL 短（6h）；③ 引用存活校验会清掉"文章已变"的旧答案。但**我不会说"绝不会返错"**——真正的解法是把用户 👎 反馈接进缓存失效逻辑（命中被差评就删缓存），这是下一步。
6. **为什么不用 Redis 存缓存、非要用 pgvector？** → 缓存的本质查找是**向量近邻**，Redis 在这个项目里没有向量检索能力（我也没有为了缓存去引一套 Redis Stack）。pgvector 已经在用、维度一致（1024）、还能顺手做"用户范围 + 时间窗"过滤，所以复用它是最小改动。另外单用户缓存只有几十条，**精确扫描比 ANN 更稳**，我没建向量索引。
7. **一次 embedding 的成本和三次 chat 调用怎么比？** → 差着一到两个数量级：embedding 是短输入、按 token 极便宜；而一次问答的 chat 调用是"长上下文输入 + 长输出"三次。所以命中一次就是净赚，未命中多一次 embedding 也几乎可以忽略——**这就是我敢把它放在请求前链路的依据**（未命中路径只多一次 embedding，不影响主链路正确性）。
8. **为什么流式也要接缓存？** → 因为流式是主入口。命中时我把答案**按 40 字切片**走同一条 `delta` 回调通道，最后照常发 `done`——前端协议完全不变，不需要为缓存写第二套渲染逻辑；同时补记一次会话记忆，保证多轮上下文连续。

**别主动说**：别说"缓存命中率高"（没有线上数据）；别说"命中不扣配额"（当前是扣的）。

## 4. v6 新增送命题

1. **"这些改动上线了吗？有数据吗？"**（最可能被问）
   → 照实说：**"代码已实现，编译和单元测试都过了；但评测集对比数据和线上冒烟我还没跑完——本地跑评测需要 ES、pgvector 和全部服务一起起来。我不拿没测过的数据当结论。"然后立刻接下一步**："下一步就是用 recall@5/10 把分块和 RRF 前后的数据拉出来对比。" **主动交代未验证部分，比被追问出来强得多。**
2. **"为什么不直接用 LangChain/LlamaIndex 的检索器？"**
   → 概念等价 + 工程可控：分块器的重叠边界、RRF 的稳定性（同分按 id 排序保证可复现）、两路降级策略这些都需要能改能测；我这套是**几十行纯逻辑 + 单测覆盖**，可读可改，比引一个大框架更容易在业务里调。
3. **"RAG 现在这么成熟，你这不就是调 API？"**
   → 区分"调用"和"工程"：调 API 解决的是"能答"；我做的是**"答得准且答得起"**——分块粒度决定召回能不能命中长文后半段、RRF 决定术语查询会不会扑空、缓存与按需触发决定成本。再给一个具体证据（最容易讲的）：**"分块器第一版有个 bug——重叠区在句子边界恰好落在块尾时截出来是空串，重叠静默失效，是单测跑出来的。"** 这句话最能证明是自己写的。
4. **"两路召回都改了，出错怎么定位？"**
   → 分层可观测：BM25 端点打 `[Bm25Recall] query/topK/hits`，融合处打 `[HybridRecall] vector=n, bm25=m, fused=k`，缓存打 `[AiSemCache] 命中/相似度/id`；缓存命中率有独立指标（`ai_semcache_hit`）。**降级路径本身也是可观测的**（fallback 里打 warn）。
5. **"改动这么多，怎么保证不把原有链路搞坏？"**
   → 三个开关 + 分层降级：`ai.retrieval.chunk-enabled`、`ai.retrieval.hybrid-enabled`、`ai.semantic-cache.enabled` 都能一键回滚；BM25 挂退纯向量、向量挂退纯 BM25、缓存任何异常按未命中处理（fail-open）；检索链路之外（发布、审核、支付）零改动。
6. **"如果让你重做一遍，你会怎么改？"**
   → ① 分块器一开始就把**重叠边界**当第一类测试用例（那个 bug 就是漏了它）；② 分块/RRF 一上线就接评测跑分，而不是等功能都写完再补数据；③ 缓存命中应该不消耗配额（扣减下沉到成功之后）。
